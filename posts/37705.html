《大规模 C++ 软件开发》读书笔记 [WIP]

Posted on 2026-10-08 Edited on 2026-11-27 In 学习笔记

感觉到了的东西, 我们不能立刻理解它, 只有理解了的东西才能更深刻地感觉它

重用来自于分解和稳定: 上层的应用可以经常变化, 底层的库应该保持稳定; 分解应该是分层的, 层次越低粒度越细, 影响面越广, 越应该稳定

设计分为物理设计和逻辑设计, 逻辑设计受限于物理设计

逻辑设计

面向对象

依赖关系

B xxx A:

  • Is a:

  • use in the interface: 对外接口中使用了 A

  • use in the implementation: 在实现中使用了 A

    • Holds: 拥有 A 的指针, 只需要前向声明 A
    • Uses: 在函数体中使了 A (的调用 / sizeof / 传递给别的函数), 对 A 的依赖程度看具体用到了什么
    • Has: 成员变量中有 A, 需要知道 A 的布局
    • Was: 私有继承 A, 还需要知道 A 的成员函数签名等

  • use in name only: 只使用了 A 的名字, 不关心 A 有什么性质

  • in structure only: 要求 A 满足一些性质

一些原则?

  • 开闭原则: 软件应该对扩展开放, 对修改封闭; 在面对需求变化时尽可能 靠增加插件而非修改代码 解决

物理设计

链接

链接属性

  1. 外部链接意味着，一个名字所指代的实体可以通过其他翻译单元中的声明被引用。
  1. 内部链接意味着，同一个翻译单元内的不同声明可以指代同一个实体，但这种身份不会通过该名字延伸到其他翻译单元。

匿名 namespace 用来平替 static 可能更好用

  1. 无链接意味着，这个名字不具有跨声明建立同一实体身份的链接属性。

绑定

我们将物理链接的过程成为绑定, 与逻辑链接区分

  1. 内部绑定: 编译翻译单元的使用时就已确定这个名字的定义, 不需要跨翻译单元工作
  2. 外部绑定: 需要跨翻译单元, 不能重复定义
  3. 双重绑定: 需要跨翻译单元, 但可以重复定义, 例如 inline 修饰的函数和变量

不光是 inline 修饰的函数和变量, 类类型定义、函数模板定义、类模板定义 都可以多个翻译单元有相同定义而不违反 ODR

这一设计主要都是为了能让多个要用到 这个类 (的成员)、模板实例化 的地方都能够得到足够的信息——模板实例化是在编译阶段进行的, 所以需要完整的实现, 因为链接器是比较独立于 C++ 语言之外的

需要注意的是, 模板函数的显式特化并不是模板函数, 而是普通的函数, 所以也具有外部绑定

  • 决定 A 和 B 哪个更基础, 然后重新组织为单向的依赖关系
  • 用上层 utility 类提供 A 和 B 的非成员相互转换:

降级

A 和 B 循环依赖

抽出其公共的部分, 让 A' 和 B' 都改为依赖这个公共的部分

不透明指针

低层级的组件 A 不应该直接调用高层级 B 组件的函数, 而是通过向更高层级 C 返回 B 的不透明指针 (Holds 关系), 让更高层级来负责调用

如果⼀个指针所指向的类型的定义不包含在当前的编译单元中, 这个指针就被称为是不透明的

哑数据

有些时候我们可以比不透明指针更进一步, 不止是指针

比如类 A 有一个类 B 数组, 还依赖于一个类 C, 会对 B 数组的一些元素进行挑选、记录或传回等不需要 B 内部实现的操作

C 可以直接不知道 B 的名字, 只需要把要处理的 B 元素的下标发送给 C; 这里的下标就是哑数据

冗余

类似多线程的通过复制避免同步

A 和 B 当前在实现上有相同的部分 不代表 一定要抽出来合并

回调

一种控制反转手段

允许在低层级执行高层级的自定义操作

管理器类

和升级差不多? 可能区别就是管理器类不止是提供 utility, 而是真正拥有并管理底层类 (负责其生命周期)

比如 graph 管理 edge 和 node

分解

类似降级, 比如 A B 循环依赖不好解决, 我们可以抽出 A B 必须循环依赖的部分放在一个组件 AB 里, 剩下的 A’ 和 B’ 分别依赖组件 AB

升级封装

wrapper 类

感觉主要就是增加一层接口, 避免上层依赖底层的实现方式

组织层次

组件

.h + .cc

设计的基本单位, 设计的目标是可以不做修改就从系统中提出来, 在其他地方复用

组件的逻辑接口就是用户能从组件中使用的东西

组件的物理接口就是 .h 中的所有东西

  • 头文件应该自己能通过编译 且只需要 include 能编译所需的其他头文件
  • 需要了解实现细节的类/函数应该放在一个模块里
  • 一个组件应该只有一个公共类; 私有类可以通过嵌套(次优)或者放在匿名 namespace 里
